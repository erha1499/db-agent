## 开发回归与新验收

- **dev：v2 全部 24 题。** 每题所有字段保持一致，仅将 split 统一设为 `dev`。旧 ID 中的 `holdout_` 和 `v2_` 用于追溯历史，不代表仍未参与开发。v2 文件及旧报告保留原样。
- **holdout：独立新增 8 题。** 预期来自人工固定账本与背景生成公式，未使用模型答案或运行参考 SQL 的结果。每题要求一次真实业务查询，查询过程中的结构读取和语义阶段仍计入原预算。

本次产品设计为独立 `QueryIntent` 提取、代码完整编译与保守 AST 选择、一次最终复核，再进入原受控执行链路。主候选不进入需求提取上下文。新题在该语义设计冻结后确定；基于已暴露 v2 失败补充的 ASCII 标识符要求和直接指定 SQL 的尝试执行说明，发生在 v3 首次验收之前，没有使用新题结果。创建时间、当时三段产品提示词哈希及全部产品 Python 源码快照见 JSON 的 `created_at` 和 `provenance`；每次正式报告还必须记录实际运行时源码哈希，不能用创建时快照冒充之后的实际运行版本。

首次 Agent holdout 验收预先固定为 **2 轮、8 题，共 16 次**。必须保留所有尝试，包括模型、环境、预算和数据错误；不补跑挑绿、不改旧 oracle。一旦根据这 8 题调整产品提示或规则，它们即转为已暴露回归，不再称为独立新验收。这里的独立仅描述未用新题结果调参，不代表共享数据、人工选题的小样本具备统计无偏性。

## 独立预期与失误见证

每题的详细手算过程写在 JSON 的 `oracle` 中；`prompt` 只有业务任务，运行时输入仍是“原业务字典 + 空行 + 题目”。参考 SQL、预期行、oracle、版本与冻结哈希不发送给模型。

| 新题 | 独立推导与需要识别的错误 |
| --- | --- |
| 排除未支付状态和零金额 | 固定订单中取消订单 3、待支付订单 5、零金额订单 4 应排除；保留订单按金额升序为 6、7、8、2、1。状态或金额条件漏一个都会多行。 |
| 恰好一单的客户 | 八名客户订单数为 2、2、1、0、1、1、1、0；只选恰好一单，客户降序为 7、6、5、3。非零 HAVING 不能省略，也不能因为 LEFT JOIN 就返回所有客户。 |
| 至少两笔成功支付 | 订单 2 的两笔成功流水为 40+50，订单 8 为 40+40；其余固定订单成功流水不足两笔。必须按流水计数，阈值 `>=2` 与 `>2` 有实际差别。 |
| 背景支付秒边界 | 客户 1000 的背景序号为 `i=1000*k`，订单 ID 为 `1000+1000*k`，支付时间是创建后 60 秒。指定支付区间取 k=0、1，降序为订单 2000、1000；k=2 恰好在上界。错用创建时间仍可能返回两行，所以同时核对 ID 和时间原值。 |
| 明细折扣列与顺序 | 订单 2 的两行分别为 `2×40−10=70`、`1×20−0=20`。按明细序号倒序，分别核对商品、数量、单价、折扣、行净额的列位置，不能以一种金额替代另一种。 |
| 保留全部 east 客户分组 | east 固定客户是 1、4、6；订单数及毛额分别为 2/190、0/NULL、1/60。按订单数排序为 4、6、1，不能擅自增加 HAVING 丢掉零订单或其他分组。 |
| 退款完成端点 | 退款 61 恰好在完成时间下界，应包含；退款 62 恰好在上界，应排除。按申请时间筛选会反选另一笔 25 元退款，因此核对退款 ID 和两种时间，不只比金额。 |
| 失败退款的非空完成时间 | 唯一固定失败退款 83 的 completed_at 为 NULL；其他已完成退款状态为 succeeded。两个条件同时满足时应为零行明细，不能改条件、填日期或混成一行聚合结果。 |

新题覆盖了数量筛选与合法无 HAVING 对照，保留了能暴露已知漏筛模式的 LEFT JOIN 场景；没有靠减少样本或增加 LIMIT 绕过执行风险。背景题通过客户条件限制到已知队列，真实计划是否通过仍由原 SQL 模式和连接器验证。所有新参考 SQL 都在现有只读语法与六张电商表范围内；静态检查通过不等于真实计划或业务验收已经通过。

## 执行与报告

创建本套件时仅离线构造和核对；未调用模型或数据库。评测入口通过受限 `--suite v3` 选择此套件，使用以下独立命令记录 SQL 基线、全部旧回归和新题首次验收；默认套件及旧命令保持兼容。

```bash
uv run python scripts/evaluate_ecommerce.py --suite v3 --mode sql --split dev --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v3 --mode sql --split holdout --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v3 --mode agent --split dev --repeat 2
uv run python scripts/evaluate_ecommerce.py --suite v3 --mode agent --split holdout --repeat 2
```

运行应继续校验精确本地 `127.0.0.1:13306/db_agent`、`db_agent_reader` 与现有授权交集，不扩大权限。SQL 与 Agent 模式分别报告；成功应同时满足实际结果、顺序、列位置、完整性和执行状态。拦住错误 SQL 但未完成应成功的任务仍计业务失败，不能用“安全停止”代替正确完成。

报告仅写入忽略的 `outputs/evals`，绑定套件、案例、共享字典、实际输入、源码、模型配置和重复次数，并保留完整分母及逐题失败。查询回答的程序渲染、意图提取、最终复核、数据库策略与真实结果分别判断；模型表示匹配不构成数据库权限或自然语言等价证明。其他产物及环境边界沿用 [评测说明](README.md)。
