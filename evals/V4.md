## 套件边界与冻结

- **dev：v3 全部 32 题。** 除统一设置 `split=dev` 外，逐字段保留，不删除失败题，也不改变 SQL、题目或预期。旧 ID 中的版本或 holdout 前缀只表示历史来源。
- **holdout：独立新增 8 题。** 使用新的业务关系、指标和控制场景，不以更换旧题数字构造新验收。它们没有参与产品调整，预期独立来自人工账本及背景商品公式。

新题独立构造，在基于旧 v3 错误的修复期间已经开始准备；不能宣称题目生成一定晚于最后一次源码修改。新题内容及人工预期确定后未改，首次执行前才最终冻结产品，并更新来源元数据，未根据任何新题结果调整提示或规则。JSON 的 `created_at` 记录套件创建时间，`product_freeze_captured_at`、三段提示词哈希和产品源码快照记录之后的最终冻结状态。每次执行报告还应绑定实际运行源码，不能把创建时间或之前的快照冒充实际版本。

新题首次验收预先固定为 **参考 SQL 1 轮（8 次）、真实 Agent 2 轮（16 次）**。每题只要求一次真实业务查询，主生成、意图提取和最终复核仍共享 4 次模型调用、6 次工具调用、60 秒总时限和每次 1024 token 的预算，不重试挑绿。SQL 模式与 Agent 模式分别统计；任何失败都保留，不能以安全拒绝代替应成功任务的完成。

这些题只在没有根据其结果调整产品时具有本次留出角色。若后续修改依赖新题结果，需将它们标记为已暴露回归。共享合成账本、人工选题和小样本仍限制结论，不能由留出通过率推导广泛统计准确率或生产安全保证。

## 新题与人工预期

每题完整推导见 JSON 的 `oracle`。只有原有业务字典与题目进入模型，参考 SQL、预期值、oracle 和冻结资料都不作为模型输入。

| --- | --- |

| 商品购买件数前四 | 商品 1 共6件/3行，商品 5 为4件/1行，商品 2、3 各2件/2行。按数量降序、ID升序为1、5、2、3。件数与行数不同，取消订单的商品3明细也在题目范围内。 |

新题均使用当前单表或显式 INNER/LEFT JOIN、基础表达式及批准聚合，不需要新函数、子查询或额外预算。商品排名中的 LIMIT 4 来自明确的前四需求，作用范围是固定订单的十条明细，不用于掩盖大扫描。其他题不添加 LIMIT。DESC、JOIN 聚合过滤、列间时间边界和 NULL 完整分组均继续覆盖，真实计划由现有规则独立判断。

## 运行方式

创建本套件只做离线构造、账本核对和静态校验，未调用模型或数据库。受限 `--suite v4` 入口使用以下命令分别保留基线、完整旧回归及新题首次验收：

```bash
uv run python scripts/evaluate_ecommerce.py --suite v4 --mode sql --split dev --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v4 --mode sql --split holdout --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v4 --mode agent --split dev --repeat 2
uv run python scripts/evaluate_ecommerce.py --suite v4 --mode agent --split holdout --repeat 2
```

沿用精确本地 `127.0.0.1:13306/db_agent`、`db_agent_reader` 及已配置的授权交集，不扩大表权限，不放宽扫描、排序、结果或时限规则。报告仅写忽略的 `outputs/evals`，记录实际输入与源码哈希、模型配置、原始分母、每次结果及失败类别。程序展示可靠性、模型需求理解、最终复核和真实查询数据分别判断，不能以模型的 match 替代权限或业务预期。其他环境和产物边界见 [评测说明](README.md)。
