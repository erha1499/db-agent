# PostgreSQL CASE 业务验收

`scripts/evaluate_postgres.py` 使用真实配置模型和 PostgreSQL 18.6 的受控只读连接器，验证自然语言需求、实际元数据、需求合同、最终语义复核、普通 EXPLAIN 和业务 SELECT 的完整链路。它不是替身测试，也不以仅连接成功或模型说成功作为通过证据。

这是公开、固定、已经用于开发验收的 `postgres-case-v1` 套件，不能作为无偏正确率、生产表现或通用 SQL 等价证明。问题、独立预期和比较方法在脚本中公开；调整产品后重跑是新的暴露回归，保留旧报告与失败，不用补跑替换原分母。

## 运行方式

先按 [PostgreSQL 本机环境说明](../infra/postgres/README.md) 建立并核验隔离环境。脚本只接受当前仓库 `.env` 明确配置的 `postgresql` 数据源：`127.0.0.1:15432/db_agent_pg`、`business` schema、`db_agent_reader` 账号，表白名单必须恰好为 `customers`、`orders`、`order_items`。它不读取管理员凭据、不导入 fixture、不更改配置或权限，不触及已有 MySQL 环境。

在仓库根目录显式运行：

```bash
uv run python scripts/evaluate_postgres.py --run --repeat 1
```

`--repeat` 仅接受 1 或 2，表示运行前约定的完整六题轮数。每题使用新的连接器和 Agent 上下文，不传历史、旧 SQL、查询结果或业务知识；失败题不自动重试，也不在后续题中注入答案。运行产品源码、fixture 或配置发生变化时停止，其余计划项仍保留在分母内。

脚本固定原默认模型预算：最多 4 次模型调用、6 次工具调用、总时限 60 秒、单请求 30 秒、请求输出上限 1024 token；产品模型请求不重试。分析、查询和元数据预算也显式固定原默认值，环境变量不能把它们放宽。1024 是发送给提供方的请求参数，不是本地硬 token 计量保证。每道题的三阶段模型调用共用原预算。

开始与结束时，脚本通过真实 reader 连接器核对版本及最小只读身份，并经 `QueryService` 完整预检读取三张小表的相关字段，与固定 fixture 核对。这些前后探针不进入 Agent 上下文、不计入单题 Agent 工具预算；它们与自然语言题的执行证据分别记录，也不是跨整个评测窗口的一致性快照。

## 六题与独立预期

| 任务 | 独立预期 | 边界 |
| --- | --- | --- |
| 全部订单按 paid、cancelled、refunded 分别计数和求和 | 一行：`3, 130.00, 1, 50.00, 1, 50.00` | 取消和退款原始金额不当作收入；不同状态分别聚合 |
| 按全部客户 LEFT JOIN 订单统计 paid | 客户 1 至 5 的数量/金额依次为 `2/130.00`、`0/0.00`、`1/0.00`、`0/0.00`、`0/0.00` | 客户 4 无订单仍保留，客户 3 的零元 paid 订单仍计数 |
| paid 且金额超过 1000，CASE 均无 ELSE | `0, NULL` | COUNT 不计 NULL，SUM 的无匹配结果保留 NULL |
| 按 created_at 统计 2026 年 2 月的 paid | `2, 30.00` | 左闭右开，创建时间不带时区，不换成支付时间 |
| 按 paid_at 的 UTC 时刻统计 2026 年 2 月的 paid | `3, 130.00` | 1001 于一月创建、二月支付；`+08:00` 输入按同一 UTC 时刻比较 |
| 关联订单与明细统计 paid 件数和明细净额 | `5, 130.00` | 折扣作用于整行；不因一单多明细而重复累加订单金额 |

预期由 [公开 fixture](../tests/fixtures/postgres_business.sql) 独立人工推导：1001 和 1002 分别为 100.00、30.00，1004 为零元 paid；1003 为取消 50.00，1006 为退款 50.00，1005 为待支付零元。paid 明细件数为 `2+1+1+1=5`，净金额为 `80+20+(35−5)+0=130`。这些数字与表行只存在于评测器比较和本机报告中，不发送给模型；题目可以明确字段、口径、日期、列顺序和 CASE 要求，但没有参考 SQL 或答案。

## 通过与记录规则

每题必须有一次真实 `execute_query` 和对应完整报告、真实结构读取、完整需求合同及 `match` 复核；模型与工具次数均在原预算内。报告须 `status=ok`、`decision=ALLOW`、`execution_status=completed`、无错误、无截断，列别名/顺序和全部行与独立预期一致。实际执行 SQL 还须包含题目要求的 searched CASE 数量；绕开新语法的结果不能充当 CASE 能力验收。最终答案核对为可信报告的确定性展示。

数量必须来自整数类型，或可精确验证为整数的 decimal 字符串；金额必须为 decimal 字符串。比较使用精确 Decimal，不接收浮点或容差、不经 JavaScript Number。`0` 与 `0.00` 仅在确认为 decimal 后按相同数值比较；NULL 仍严格为 NULL，行序、列位置和重复行保留。

报告写入忽略的 `outputs/evals/postgres/<run_id>.json`，文件权限 0600；记录 UTC 起止时间、计划/实际/通过/失败/未运行分母、模型名称、固定预算、源码/fixture/依赖/环境脚本哈希、实际 SQL、查询报告、合同和复核 observation、前后 fixture 探针及配置/源码是否变化。不会记录 API key、base URL、数据库密码、完整连接串或原始异常堆栈。运行记录在每题后落盘，未完成的计划保留；单次题目失败不阻止后续独立题，环境或来源变化停止整组。

退出码 0 表示整个预定套件及前后环境证据均通过，1 表示有失败、缺证据或来源变化，CLI 参数错误为 2，键盘中断入口为 130。若发生进程强杀或磁盘写失败，已落盘报告可能仍含未运行项，不能据此宣称完成。

规则单测、真实数据库集成、真实模型业务验收与 GitHub CI 分别汇报，不能互相替代。
