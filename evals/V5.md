# 电商验收套件 v5

> 历史冻结说明：v5 首轮结果保留在 [业务验收记录](../docs/ecommerce.md)。随后其中的反关联查询用于定位 `not_exists` 计划兼容缺口，因此现在全部题目仅作已暴露回归；JSON 与首轮报告未修改。下文记录首次运行前的约定，不代表当前重跑仍是未参与开发的验收。

[v5 案例文件](ecommerce-v5.json) 继续使用冻结的 `ecommerce-v1` 数据：1000000 订单、100000 客户、10000 商品，seed 为 `20260910`。v4 全部 40 题逐字段保留为 dev，仅改 split；共享业务字典和数据要求不变，原 [v4 JSON](ecommerce-v4.json) 及所有旧报告保留原样。

新增加的 8 道 holdout 由人工账本和背景公式独立推导，不来自模型输出、候选执行结果或生成器汇总。它们在旧题修复期间开始构造，题目、参考 SQL 和预期固定后不再改变；首次执行前再记录最终产品源码与提示词哈希，不能宣称题目一定晚于全部代码改动才开始编写。

## 本次产品冻结与验收约定

已暴露的 v4 开发任务出现过 SQL 内容正确，但模型复述出处时抄错标点导致拒绝的情况。此次简化删除模型返回的 `goal_quote` / `source_quote`，由运行时代码计算原始请求的 SHA256 进行绑定。完整查询合同与未决问题、代码编译及保守 AST 选择、独立最终复核、原 QueryService 和连接器的强制 SQL 检查均保留，预算不增加。

请求哈希只绑定代码实际持有的原始输入，不能证明模型完整理解该输入。移除模型抄录原文的字段，也不意味着可以省略行筛选、HAVING、时间、列顺序或风险规则。由于 v4 留出结果已被查看，之后的 v4 重跑仅作已暴露回归；本版新题不参与此次修改。

JSON 的 `created_at` 记录套件创建时间，`provenance` 记录后续最终冻结时间、三段产品提示哈希及产品 Python 源码快照。正式报告还必须绑定实际运行版本、完整套件、案例、业务字典和发送给模型的实际输入。题目内容在来源元数据最终更新前已固定，不依据新的 SQL 或模型结果调整。

首次验收预先固定：

- SQL 基线：dev 40 题、新 holdout 8 题各 1 轮。
- 真实 Agent：dev 40 题 1 轮，新 holdout 8 题 2 轮，共 16 次新题尝试。
- 每题 1 次真实业务查询；主生成、独立意图提取和最终复核共享 4 次模型调用、6 次工具调用、60 秒总时限、每次 1024 token 的原预算。

必须保留超时、模型协议、预算、计划拒绝与数据错误等全部结果，不补跑挑绿、不改旧 oracle。拦住错误 SQL 但没有完成应成功任务仍计业务失败。若后来依据 v5 结果调整产品，这些题也应转为已暴露回归；共享合成数据和小样本不支持广泛准确率或生产安全结论。

## 新题的业务口径与人工推导

每题的详细算式写在 JSON 的 `oracle`。只有原业务字典与业务问题进入模型，参考 SQL、预期结果、oracle、源码哈希等评测资料都不进入模型消息。

| 新题 | 需要验证的业务区别与独立预期 |
| --- | --- |
| 有折扣订单的全部明细汇总 | 只有订单2总折扣大于0，必须连同第二条零折扣明细一起汇总：折扣10、折前100、折后90、两行。若提前在WHERE筛掉零折扣明细，就错误变成折前80、折后70、一行。 |
| 单笔支付的部分退款余额 | 支付23金额50、成功退款30，余额20；支付81、82各40、成功退款各20，余额各20。支付61已全部退回，余额0，不能入选。失败或待处理退款不计，支付原额不能按多笔退款重复累加。 |
| 二月创建但月底未支付 | 二月创建订单2、3、4、5、6中，2和4已在二月支付；3、5尚无支付时间，6在三月才支付。按ID倒序返回6、5、3，不能用当前退款状态替代历史支付时间。 |
| 下过单但从未有已支付订单的客户 | 客户5仅有pending订单5，是唯一答案。客户2虽然有取消订单3，但还有已支付订单6，不能入选；客户4、8完全无订单，也不符合“下过单”。用同一订单表的两份别名区分全部订单与已支付订单，不使用子查询。 |
| 完整支付原因分组 | 固定支付12条：8条成功金额380，一条pending金额25，它们的failure_reason均NULL；该组是9条尝试、8条非空paid_at、金额405。三个失败尝试原因均为synthetic_decline，金额100+90+50=240，paid_at非空笔数0。NULL原因不等于一定已支付。 |
| 背景创建与支付时间跨度 | 客户1000有k=0..999共1000单，创建为12:00:00+k秒；最晚创建12:16:39。支付均晚60秒，最早12:01:00、最晚12:17:39。四个时间极值分别对应原字段，不能只算一组后复用。 |
| 单笔退款超过对应支付的异常 | 六笔成功退款与对应支付金额分别为10/50、20/50、25/50、25/50、20/40、20/40，均未严格超过。应返回零行明细；累计退款与单笔退款是不同判断粒度。 |
| 多件且未打折的明细 | quantity至少2且折扣0的明细属于订单1、7、8，折前金额分别80、60、80；订单2虽然两件但有折扣，应排除。金额降序、同金额订单ID降序得到8、1、7；两条商品1记录不能被合并成商品统计。 |

新题重组了订单、支付、退款和明细的关系，继续检验多条件、行与组筛选、NULL 完整对照、列间或日期边界、金额来源、件数与行数、顺序和空结果。所有题均限于现有单表或显式 INNER/LEFT JOIN、批准聚合及基础表达式，不需要额外函数、子查询或新权限。没有新题用 LIMIT 缩小或掩盖真实扫描风险；客户1000题仍由原索引范围和计划规则约束。

## 运行与证据

创建时仅做离线构造、账本复核与静态检查，未调用模型或数据库。使用受限 `--suite v5` 入口分别运行并保存：

```bash
uv run python scripts/evaluate_ecommerce.py --suite v5 --mode sql --split dev --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v5 --mode sql --split holdout --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v5 --mode agent --split dev --repeat 1
uv run python scripts/evaluate_ecommerce.py --suite v5 --mode agent --split holdout --repeat 2
```

执行仍限定 `127.0.0.1:13306/db_agent`、`db_agent_reader` 和已有电商表授权交集。不得扩大权限、提高扫描阈值或运行预算。SQL 与 Agent 的分母、数据与语义失败、环境及超时分别记录；模型 match 不等于数据库允许，也不证明自然语言等价。

产物仅写入忽略的 `outputs/evals`，保留每次真实结果、实际 SQL、必要合同与复核证据及来源哈希。历史错误候选 fixture 重放是单独的定向控制流程证据，不能代替这里的真实生成、完整任务和新留出验收。其他边界沿用 [评测说明](README.md)。
